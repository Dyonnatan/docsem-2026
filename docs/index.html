Investigating a Guided-Reasoning Pipeline for Open Models Under a Validation–Test Shift

DFM at DocSEM 2026

Open-weight models are cheaper to run and easier to inspect than closed ones, but they are usually evaluated as they are: one prompt, one answer. We keep the weights frozen, change only what surrounds the model call, and ask whether that alone solves document-grounded math better.

Motivation

Open-weight models

Cheaper to run and easier to inspect than closed models, but usually evaluated as they are: one prompt, one answer.

Usual routes

Strong results on tasks like this one come from closed models, which can change or be retired, or from further training with reinforcement learning or fine-tuning, which needs GPUs and labelled data.

A third route

Frozen weights. Following the growing use of prompt engineering, agents and harnesses, only what surrounds the model call changes: what the model writes, code for the arithmetic, rules on the output, and agent-like roles.

Research questionCan frozen open-weight models solve document-grounded math better with inference-time guidance alone?

Task and test-set shift

in
rendered PDF, no text layer+paraphrased query
out
numeric answer+supporting block ID

The system reads the document, finds the passage the query refers to, and returns the numeric answer with the ID of the block that supports it. The problems are semantic variants of grade-school math word problems. Ranking uses joint exact accuracy: answer and evidence must both be exactly right.

Validation and test turned out to be quite different tasks.

validationtest
characters per document~5k~43k
quantitative problems per document123.6
decoys that repeat the query's wordsnoyes

Decoys repeat the words of the query inside a counting template, while the real target mentions its subject only once, in ordinary prose.

So on test, the system must first select the passage and only then resolve it, and keyword overlap often points to the wrong block. Everything tuned during development addressed resolution. Neither training nor validation data can measure selection, because each of their documents holds a single candidate.

Method: pipeline variants

The model stays frozen; only what surrounds the call changes. Each variant changes one design decision relative to the previous one and is compared with it by exact McNemar tests on paired items. Stage 1, which transcribes each rendered page to markdown with MinerU2.5-Pro, ran once and is shared by all variants.

A0
Direct
Query and document in, answer and evidence out.
C2
Rival readings
Two competing readings of the passage, each an arithmetic expression that Python evaluates. Validators reject a reading that uses fewer of the passage's numbers than its rival (V2), misreads a tiered rate (V4), or fails to evaluate (V5).
C3
Compiled steps
Each reading is a short list of steps in a small domain-specific language (DSL): observe a quantity (obs), state an assumption (assume), compute (therefore) and return. The model reads; the code computes. Reimplementations of PAL, SatLM and ArgLLM in the same harness did not outperform it in an exploratory test on hard cases.
C3C
Notebook and reviewer
A notebook, a kind of contextual memory with rules for recurring ambiguities, and a reviewer that labels each surviving reading with a side from a closed set. A fixed rule picks a reading when the labels separate them. The submitted system.

Other models tested

The variants were explored with 14 open-weight models. Only two reached the main results: DeepSeek-V4-Flash, chosen for the submitted pipeline, and GLM-5.3-Flash, added for the replica. Each model is compared with DeepSeek-V4-Flash on the same tasks; the metric changes by block.

The submitted pipeline

A vision model transcribes each PDF once, and the analyst model writes two rival readings as DSL steps. Code compiles and evaluates them, and the validators filter them. If one reading survives, it is committed. If several survive, a reviewer labels them and a notebook rule picks one when the labels separate them; otherwise the analyst's preference is kept. Finally, the evidence is narrowed to the block the committed reading used.

Who decided each answer

The structure constrains and records the model's reasoning, but on the test regime the final choice is almost always the model's.

Test labels are hidden, and training and validation cannot measure selection. After the competition deadline we therefore built a labelled replica of the test regime: 300 training problems, whose answer and evidence are public, re-embedded into documents generated from the test template. Each document carries about 22 competing problems, decoys that repeat the query's words, printed values of other cases, and opaque block identifiers. Its answer accuracy is within three points of the first test submission.

Where the errors are

On the replica, we split the errors into selection errors, where the cited block is not the target, and resolution errors, where the target is cited but the number is wrong.

Validators, the DSL and the notebook were designed for resolution. If they leave the cited passage unchanged, they can fix at most 7.3% of tasks.

The poster and the talk presented at the workshop showed an earlier version of this analysis (52.9% and 7.6% on 291 tasks, from the C3 outputs before nine parse failures were re-run). The paper, this page and the poster and slides linked here use the submitted system on all 300 tasks.

Results on the replica

The structure aimed at resolution adds little. The largest gain came from a task-specific instruction: one paragraph added to the analyst's prompt after the deadline, written by inspecting unlabelled test documents. It describes the decoy template and asks the model to match the query to what a problem is about, not to repeated words.

Takeaways

  1. Target guidance at where the errors are.
    A short, targeted instruction can matter more than an elaborate reasoning structure. One paragraph on passage selection gave the largest gain of all variants.
  2. Structure makes reasoning inspectable, not necessarily better.
    Rules rarely override the model's own choice: the analyst's preference decided 274 of 300 replica answers. The trace did let a rule scope the evidence of the test submission to the committed reading, which cut multi-block citations from 455 to 66.
  3. Copies of one model are not independent reviewers.
    They tended to agree on the same wrong reading: an early jury of three, played by the analyst's own model, matched gold in 0 of 19 decisions on the hard training subset. With 19 decisions this observation is exploratory.
  4. Scaffolding helps, but the model matters as much as the technique.
    A stronger model alone can outperform a scaffolded weaker one: GLM-5.3-Flash prompted directly beats DeepSeek-V4-Flash with C3 (61:16, p = 2×10⁻⁷).

Our ranked submission reached 45.09% joint accuracy on test, against 85.09% for the best entry. The replica and the selection guidance were developed after the competition, for analysis only.

Limitations. All results come from one benchmark of grade-school math variants. The card was derived from test documents after the deadline, and 65 of the replica's 300 targets come from the development corpus. Every arm is a single run, and the closed-agent comparison is not controlled: the agent ran once, interactively, with code execution.

Reproduce

The repository contains every prompt, the replica and its generator, the stage-1 text of all documents, and the completions of every model call behind the paper's tables. The package uses only the Python standard library.

git clone https://github.com/Dyonnatan/docsem-2026.git && cd docsem-2026
pip install -e ".[dev]"

dfm tables                     # recompute the paper's tables, no API calls
dfm replay configs/*/*.json    # rebuild every prediction from its completions
dfm replica build --out /tmp/r # regenerate the replica byte for byte
pytest

dfm run configs/replica/c3-card-glm.json   # new run, needs OPENROUTER_API_KEY

The figures that the revised paper corrects relative to the camera-ready version and to the material presented at the workshop are listed in docs/REPRODUCING.md.
